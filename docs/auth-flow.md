# 🔒 Аутентификация, сессии и подтверждение через uCaller (`docs/auth-flow.md`)

Система безопасности и аутентификации построена на базе модуля **`nuxt-auth-utils`**, реляционной базы данных PostgreSQL (модель `users` с нативным перечислением ролей `UserRole`), **Redis** для временного хранения черновиков регистрации и сервиса **uCaller.ru** для Flash-call верификации номеров телефонов.

---

## 1. Сценарий регистрации (Two-Step Registration Flow)

Регистрация новых пользователей разбита на два последовательных шага (`'input'` -> `'verify'`) с обязательной проверкой предзаписанного в системе номера телефона.

### Шаг 1: Инициация звонка и создание черновика (`POST /api/auth/register/init`)

1. Пользователь вводит номер телефона и задает пароль (минимум 6 символов) на странице `/auth/register`.


2. Сервер нормализует телефон и проверяет его наличие в таблице `users`:
* Если номер не найден в базе, регистрация отклоняется (`403 Forbidden`: *«Номер телефона не найден в системе. Обратитесь к администратору»*).


* Если пользователь уже активирован (`activated_at !== null`), возвращается ошибка (`409 Conflict`).




3. Сервер обращается к внешнему API **uCaller** (`[https://api.ucaller.ru/v1.0/initCall](https://api.ucaller.ru/v1.0/initCall)`) с использованием Bearer-авторизации (`UCALLER_SECRET_KEY.UCALLER_SERVICE_ID`).


4. uCaller инициирует входящий звонок на номер абонента и возвращает код подтверждения (последние 4 цифры входящего номера).


5. Пароль пользователя хэшируется с помощью **`bcryptjs`** (с фактором сложности 10), после чего временный объект (черновик) сохраняется в **Redis** под ключом `pending_reg:<phone>` с TTL **6 минут (360 секунд)**:


```json
{
  "code": "1234",
  "phone": "79112223344",
  "password": "$2a$10$...",
  "user_id": 1
}

```


6. Клиент переключается на шаг ввода кода (`step = 'verify'`).



### Шаг 2: Подтверждение кода и активация (`POST /api/auth/register/verify`)

1. Пользователь вводит 4 цифры кода подтверждения.


2. Сервер извлекает данные из Redis по ключу `pending_reg:<phone>`. Если срок действия истек или данных нет, возвращается ошибка.


3. Проверяется совпадение введенного кода с кодом uCaller. При несовпадении генерируется ошибка `400 Bad Request`.


4. После успешной проверки временная запись удаляется из Redis (`redis.del`).


5. База данных обновляется: пользователю проставляется захешированный пароль и текущая дата активации (`activated_at = new Date()`).


6. С помощью модуля `nuxt-auth-utils` создается защищенная куки-сессия (`setUserSession`), и пользователь авторизуется в системе.



---

## 2. Сценарий входа в систему (`POST /api/auth/login`)

1. Пользователь отправляет номер телефона и пароль на эндпоинт `/api/auth/login`.


2. Сервер ищет пользователя по номеру телефона в таблице `users`.


3. С помощью **`bcryptjs.compare`** проверяется соответствие введенного пароля сохраненному хэшу.


4. При успешной проверке формируется объект сессии (`sessionUser`), содержащий `user_id`, `role_name`, `user_name` и `avatar_path`.


5. Сессия сохраняется через `setUserSession(event, { user: sessionUser })`.


6. На клиентской стороне Pinia-стор (`authLogin`) перенаправляет пользователя в зависимости от его роли (`UserRole`):
* `admin` ➔ `/admin`


* `installer` ➔ `/installer`


* `client` ➔ `/client`


* Другие ➔ `/profile`





---

## 3. Завершение сеанса (`POST /api/auth/logout`)

Очищает текущую сессию пользователя с помощью вызова `clearUserSession(event)`, удаляя авторизационные куки и сбрасывая состояние в Pinia-сторах.
