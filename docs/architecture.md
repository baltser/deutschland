# 🏛 Архитектура проекта (DNZ Architecture)

Данный документ описывает системную архитектуру, доменную структуру каталогов и принятые паттерны разработки в проекте **DNZ** на базе **Nuxt 4**.

---

## 1. Общий стек технологий

- **Фреймворк:** Nuxt 4 (Vue 3, Composition API)
- **Интерфейс & UI:** Tailwind CSS, Nuxt UI Kit
- **Управление состоянием:** Pinia (разделение по доменам: `auth`, `admin`, `client`, `installer`, `profile`)
- **Авторизация и сессии:** `nuxt-auth-utils` + **uCaller.ru** (Flash-call верификация номеров телефонов) + Nodemailer (Email verification)
- **Серверная часть:** Nitro API (`server/api/`)
- **База данных:** PostgreSQL 16 + Prisma ORM (нативные Enum-роли `UserRole`)
- **Файловое хранилище:** MinIO (объектное хранилище для аватаров и медиа)
- **Кэш и временные данные:** Redis
- **Инфраструктура & CI/CD:** Docker, Docker Compose, GitHub Actions (GHCR)

---

## 2. Клиентская архитектура (`app/`)

Клиентская часть организована по **модульному доменному принципу (Feature-First)**. Каждая роль и сущность инкапсулирует собственные компоненты, композисы, сторы и страницы.

```text
app/
├── components/          # UI-компоненты по доменам
│   ├── admin/           # Админ-панель (управление адресами, пользователями, модалки)
│   ├── app/             # Общие интерфейсные оболочки (Header, SidebarLayoutShell, PhoneInput, Logo)
│   ├── auth/            # Компоненты авторизации и загрузки аватаров
│   ├── client/          # Клиентские компоненты (списки объектов и адресов)
│   └── user/            # Пользовательские элементы (UserAvatar, ProfileBadge)
├── composables/         # Переиспользуемая бизнес-логика (по доменам admin, auth, client, installer, profile)
├── layouts/             # Макеты страниц под каждую роль (admin, auth, client, installer, profile, default)
├── middleware/          # Глобальные мидлвары (role-redirect.global.ts — защита маршрутов и редиректы)
├── pages/               # Файловый роутинг, разделенный по ролям и доменам
│   ├── admin/           # Панель администратора (addresses/, users/, system/)
│   ├── auth/            # Вход и регистрация (login.vue, register.vue)
│   ├── client/          # Личный кабинет клиента
│   ├── installer/       # Кабинет монтажника 
│   └── profile/         # Управление профилем пользователя
├── plugins/             # Клиентские плагины (auth.ts)
├── stores/              # Изолированные Pinia-сторы (admin, auth, client, installer, profile)
├── types/               # TypeScript интерфейсы и контракты данных
└── utils/               # Вспомогательные утилиты (phone, roles, logout)

```

### Ключевые особенности клиента:

* **Макеты (`layouts/`):** Поддерживают отдельные визуальные каркасы для администраторов, монтажников, клиентов и страниц авторизации.


* **Ролевой Middleware (`role-redirect.global.ts`):** Автоматически проверяет сессию пользователя и перенаправляет его в соответствующий личный кабинет (`/admin`, `/installer` или `/client`) на основе его роли (`UserRole`).


* **Типизация (`app/types/`):** Содержит строгие контракты данных для аутентификации (`auth.ts`, `auth.d.ts`), административной панели (`admin.ts`), объектов и оборудования (`address.ts`, `device.ts`), а также обработки ошибок (`error.ts`).

## 3. Серверная архитектура (`server/`)

Серверная логика реализована на базе Nitro Engine и следует строгой доменной структуре:

```text
server/
├── api/                 # API-эндпоинты, разбитые по доменам
│   ├── admin/           # Управление пользователями, персоналом, адресами и email-шаблонами
│   ├── auth/            # Сессии, авторизация, Flash-call верификация uCaller, подтверждение почты
│   ├── client/          # Доменные эндпоинты клиентов (addresses.get.ts)
│   ├── files/           # Проксирование и защищенная раздача файлов из MinIO ([...path].get.ts)
│   ├── health/          # Проверка работоспособности сервисов (minio.get.ts)
│   ├── installer/       # Эндпоинты для монтажников (devices.get.ts)
│   └── profile/         # Управление профилем, смена данных и загрузка аватаров в MinIO
├── plugins/
│   └── startup.ts       # Автоматическая инициализация при старте сервера
├── types/               # Серверные TypeScript типы
└── utils/               # Системные синглтоны и сервисы (prisma, minio, redis, logger, mail, phone, adminUser)

```

### Автоматическая инициализация (`server/plugins/startup.ts`)

Плагин автоматической инициализации Nitro запускается при старте бэкенд-приложения и выполняет последовательную проверку работоспособности всей инфраструктуры и первичное сидирование:

1. **PostgreSQL:** Устанавливает соединение с базой данных через `prisma.$connect()`. При сбое запуск прерывается критической ошибкой.


2. **Администратор:** Проверяет наличие учетной записи администратора в системе и автоматически создает дефолтного администратора с помощью функции `ensureDefaultAdminUser()`.


3. **Шаблоны писем:** Проверяет и инициализирует базовые HTML-шаблоны почтовых рассылок через `ensureDefaultEmailTemplate()`.


4. **Redis:** Вызывает команду `redis.ping()` для подтверждения стабильности соединения с кэш-сервером и хранилищем временных токенов.


5. **MinIO:** Обращается к S3-хранилищу через функцию `ensureBucket()` для проверки доступности и создания рабочего бакета (`dnz-uploads`).

## 4. Ролевая модель и безопасность

Система использует встроенный Prisma Enum `UserRole`:

* `admin` — Администратор


* `installer` — Монтажник 


* `manager` — Менеджер


* `client` — Клиент



Доступ к серверным эндпоинтам (`server/api/admin/`, `server/api/installer/`) и клиентским страницам (`/admin/*`, `/installer/*`) строго разграничен на уровне мидлваров сессий Nuxt Auth Utils и ролевых проверок.
